1. State Machine Diagram

The guest check-in workflow is governed by a 9-state finite state machine. Each state represents a required onboarding step; transitions are driven by intents detected from the guest's messages. The transition table is defined in app/state_machine/transitions.py and the state enum in app/state_machine/states.py.

Note: The self-transitions on INFO_VERIFY_PENDING (confirm and provide_info) keep the guest in the same state. confirm triggers an OTP email; provide_info lets the guest correct their details before confirming. Only verify_otp (after successful OTP verification) advances to ID_VERIFY_PENDING.

2. Agent Execution Sequence

When a guest sends a message, the SessionManager.process_message() method orchestrates the full pipeline: load session → detect intent → extract entities → route to MCP tool → advance state → generate response. The sequence diagram below shows the interactions between the core components.

sequenceDiagram autonumber participant G as Guest participant SM as SessionManager participant ID as IntentDetector participant FA as FallbackAgent participant EE as EntityExtractor participant TR as ToolRouter participant MCP as MCP_Tools participant STM as StateMachine G->>SM: process_message(session_id, guest_msg, db) SM->>SM: Load Session from DB SM->>SM: Get current State %% Intent detection SM->>ID: detect_intent(message, state) ID->>ID: _detect_intent_llm(message, state) alt Ollama LLM succeeds ID-->>SM: llm_intent else Ollama unavailable ID->>FA: detect_intent_regex(message, state) FA-->>ID: regex_intent ID-->>SM: regex_intent end %% Entity extraction SM->>EE: extract_entities(message, state) alt Ollama LLM succeeds EE-->>SM: entities dict else Ollama unavailable EE->>EE: _extract_regex(message, state) EE-->>SM: entities dict end %% Tool routing SM->>TR: route(intent, entities, state, session_id, db) TR->>MCP: Execute mapped tool MCP-->>TR: tool_result TR-->>SM: (tool_result, tools_called) %% State advancement SM->>STM: advance(intent, guest_response) or decline(guest_response) STM-->>SM: new_state SM->>SM: _enrich_response(content, new_state, session, db) %% Save & return SM->>SM: Save Guest & Agent messages to DB SM-->>G: {agent_content, intent_detected, tools_called, current_state, required_action}
Key detail: The OTP verification gate lives inside _advance_state(). When the intent is verify_otp and the tool result indicates failure, the state machine does not advance — the guest stays in INFO_VERIFY_PENDING and receives an error message with remaining attempts.

3. LLM Pipeline with Fallback

The system uses a primary Ollama LLM (Llama 3.1 8B) for intent detection and entity extraction. When Ollama is unavailable or returns an invalid intent, a regex-based FallbackAgent takes over. The flowchart below illustrates this two-tier strategy.

FallbackAgent Regex Patterns

The FallbackAgent uses an ordered list of compiled regex patterns. The order matters — more specific patterns are checked first:

  1. decline — "no", "declined", "refuse", "don't agree", etc.
  2. request_help — "I need help", "speak to someone", etc.
  3. select_option — "damage waiver", "security hold", "option 1/2"
  4. provide_info — "my name is", "call me", "update", "change"
  5. question — "what", "when", "how", or contains "?""
  6. agree — "yes", "agree", "accept", "okay", "confirmed"
  7. greeting — "hi", "hello", "hey", "good morning"

State-specific overrides run before the general patterns:

  • INIT → "start/begin/ready" → start
  • INFO_VERIFY_PENDING → "confirm/correct" → confirm; 6-digit number → verify_otp
  • ID_VERIFY_PENDING → "uploaded/sent id" → upload_id
  • INCIDENTAL_PROTECTION_PENDING → "damage waiver/security hold" → select_option
  • REFUSED → "resume/restart" → resume

Step-by-Step Walkthrough

  1. Session Creation — The guest provides a booking reference. A new session is created in the INIT state.
  2. Privacy Policy — The agent presents the privacy policy text. The guest must agree or decline. Declining sends the guest to REFUSED.
  3. House Rules — Same agree/decline pattern. Agreement is recorded via the record_agreement MCP tool.
  4. Rental Agreement — Same agree/decline pattern. Third and final agreement step.
  5. Info Verification — The agent retrieves the guest's reservation data (name, email, phone, guest count). The guest can:
    • provide_info — correct details (self-transition)
    • confirm — triggers OTP email (self-transition, stays in INFO_VERIFY_PENDING)
    • verify_otp — if OTP is valid, advances to ID_VERIFY_PENDING; if invalid, error with remaining attempts
  6. ID Upload — The agent generates a secure, HMAC-signed, time-limited link for uploading a government-issued ID. The guest uploads externally and confirms with upload_id.
  7. Incidental Protection — The agent generates a selection + payment link. The guest chooses between Damage Waiver ($49) or Security Hold ($250). Confirming with select_option completes onboarding.
  8. Completed — Arrival instructions (property address, WiFi, lockbox code, check-in/out times) are fetched and delivered to the guest.
  9. Resume from Refusal — At any REFUSED state, the guest can say "resume" to restart from INIT.
External flows: ID upload and incidental protection both use HMAC-signed, time-limited links generated by app/services/link_service.py. The guest completes these steps outside the chat widget (in a browser), then returns to the chat to confirm completion.
