3. Executive Summary

The Guest Check-In System is a conversation-based, AI-powered onboarding platform for short-term rental properties. It replaces fragmented email-link workflows with a single, guided chat experience that walks every guest through the required check-in steps — privacy policy acceptance, house rules, rental agreement, identity verification, ID upload, and incidental protection — in a natural conversation.

Who It's For

  • Property Managers & Booking Platforms — Integrate via REST API or embed the chat widget on any website.
  • Guests — Complete onboarding by chatting with an AI agent; no app download or portal login required.

Key Benefits

  • Higher Completion Rates — Guided conversation prevents guest abandonment at any step.
  • Real-Time Assistance — Guests can ask questions mid-process; the AI answers from the property FAQ.
  • Full Audit Trail — Every agreement, transition, and action is recorded with timestamps.
  • Channel-Agnostic — REST API + WebSocket + embeddable widget work with any booking channel.
  • Local LLM — Runs Ollama (Llama 3.1 8B) on-premise; no cloud API keys, no per-message cost.
  • State-Machine Safety — The AI agent can never skip a step; the state machine is the single source of truth.

4. High-Level Architecture

The system follows a three-layer architecture: Client Layer (web widget + API clients), Application Layer (FastAPI server, state machine, LLM agent, MCP tools, services), and Data Layer (MySQL + file storage).

5. Process Flow — State Machine

The guest onboarding workflow is governed by a deterministic state machine with 9 states. The LLM agent detects intent and calls MCP tools, but the state machine validates every transition — the agent can never skip a step.

At each agreement step (Privacy Policy, House Rules, Rental Agreement), the guest can agree (advancing to the next state) or decline (transitioning to REFUSED). A refused session can be resumed at any time, restarting from the beginning (INIT).

9. Deployment Guide

9.1 Prerequisites

  1. Docker — docker --version should return 20.10+
  2. Docker Compose — docker compose version should return v2+
  3. Ollama — Install from ollama.com and verify: ollama --version

9.2 Clone the Repository

git clone https://github.com/your-org/guest-checkin.git
cd guest-checkin

9.3 Configure Environment

cp .env.example .env
# Edit .env with your settings (see Section 10 for full reference)

At minimum, set DATABASE_URL, OLLAMA_BASE_URL, and LINK_SECRET (change from the default for production).

9.4 Pull the Ollama Model

ollama pull llama3.1:8b
Note: This downloads ~4.7 GB. Run ollama serve first if the daemon is not already running.

9.5 Start Services

docker compose up -d --build

This starts three containers:

  • app — FastAPI on port 8000
  • mysql — MySQL 8.0 on port 3306
  • mailhog — SMTP on port 1025, Web UI on port 8025

9.6 Run Database Migrations

docker compose exec app alembic upgrade head

9.7 Seed the Database

docker compose exec app python -m seed.seed_reservations
docker compose exec app python -m seed.seed_knowledge_base
docker compose exec app python -m seed.seed_api_keys

9.8 Verify the System

# Health check
curl http://localhost:8000/docs

# Test with demo API key
curl -H "X-API-Key: demo-key" \
  http://localhost:8000/api/v1/reservations/BK-2024-001

# Check MailHog
open http://localhost:8025

If all return successful responses, the system is running.

12. Widget Integration Guide

The guest check-in widget is a lightweight, embeddable chat bubble built with vanilla JavaScript. No React, Vue, or build step required.

12.1 Basic Integration

Add the CSS and JS to your page, then initialize the widget:

<!-- In the <head> of your page -->
<link rel="stylesheet" href="https://your-domain.com/static/chat-widget.css">

<!-- Before </body> -->
<script src="https://your-domain.com/static/chat-widget.js"></script>
<script>
  var widget = GuestCheckInWidget.init({
    sessionId: 'SESSION_ID_FROM_API',
    token:     'SESSION_TOKEN_FROM_API',
    wsUrl:     'wss://your-domain.com/api/v1/ws/SESSION_ID?token=TOKEN',
    apiUrl:    'https://your-domain.com/api/v1'
  });
</script>

12.2 Configuration Options

OptionTypeRequiredDescription
sessionIdstringYesSession ID from POST /sessions
tokenstringYesSession token for WebSocket auth
wsUrlstringYesFull WebSocket URL including token query param
apiUrlstringYesBase REST API URL (e.g. https://your-domain.com/api/v1)
themestringNoWidget theme: "light" (default) or "dark"

12.3 Event Callbacks

Subscribe to message events after initialization:

widget.callbacks.message.push(function(msg) {
  console.log('New message:', msg);
});

12.4 Customization

  • Theme — Pass theme: "dark" to init() for dark mode.
  • Position — The widget appears as a floating action button (FAB) in the bottom-right corner. Override CSS class .gci-fab and .gci-widget to reposition.
  • Progress Steps — The widget shows a 6-step progress bar automatically mapping states to steps (Privacy → Rules → Rental → Info → ID → Incidental).
  • Auto-reconnect — The WebSocket client reconnects automatically with exponential backoff (1s → 30s max) if the connection drops.

12.5 Typical Integration Flow

  1. Your backend calls POST /api/v1/sessions with the booking reference and API key.
  2. The response includes id (session ID) and session_token.
  3. Pass these values to GuestCheckInWidget.init() on your frontend page.
  4. The widget opens, connects via WebSocket, and the conversation begins.

13. State Machine Reference

Nine states govern the guest onboarding flow. The LLM agent detects intent and calls MCP tools; the state machine validates every transition.

StateRequired ActionValid IntentsNext (Success)Next (Decline)
INITInitialize check-in sessionstartPRIVACY_POLICY_PENDING—
PRIVACY_POLICY_PENDINGAccept or decline the Privacy Policy & Data Usageagree, declineHOUSE_RULES_PENDINGREFUSED
HOUSE_RULES_PENDINGAccept or decline the House Rulesagree, declineRENTAL_AGREEMENT_PENDINGREFUSED
RENTAL_AGREEMENT_PENDINGAccept or decline the Rental Agreementagree, declineINFO_VERIFY_PENDINGREFUSED
INFO_VERIFY_PENDINGConfirm personal information (name, email, phone, guests)confirm, provide_infoID_VERIFY_PENDING— (stays in state on provide_info)
ID_VERIFY_PENDINGUpload government-issued ID via secure linkupload_idINCIDENTAL_PROTECTION_PENDING—
INCIDENTAL_PROTECTION_PENDINGSelect Damage Waiver or Security Hold + paymentselect_optionCOMPLETED—
COMPLETEDNone — onboarding finished— (terminal)——

Key rule: The LLM agent never advances state directly. It detects intent and calls MCP tools. The state machine validates the tool result and transitions. This prevents hallucination from skipping steps.

14. MCP Tools Reference

The LLM agent has access to 12 MCP (Model Context Protocol) tools — internal Python functions that handle data operations. The agent calls these tools; the state machine validates results and transitions.

1. get_reservation

DescriptionRetrieve reservation details by booking reference. Returns property name, guest info, dates, Wi-Fi, lockbox code, and agreement texts.
Parametersbooking_reference (string, required) — e.g. "BK-2024-001"
ReturnsReservation object with all fields, or null if not found
Active InAny state

2. record_agreement

DescriptionRecord guest acceptance or refusal of an agreement (privacy policy, house rules, or rental agreement).
Parameterssession_id (string, required), agreement_type (string, required: "privacy_policy" | "house_rules" | "rental_agreement"), accepted (boolean, required), guest_response (string, optional)
Returns{ "recorded": true, "agreement_id": "...", "agreement_type": "...", "accepted": true/false }
Active InPRIVACY_POLICY_PENDING, HOUSE_RULES_PENDING, RENTAL_AGREEMENT_PENDING

3. update_guest_info

DescriptionUpdate guest personal information during the info verification step.
Parameterssession_id (string, required), first_name (string, optional), last_name (string, optional), phone (string, optional)
Returns{ "updated": true, "guest_id": "...", "updated_fields": [...], "first_name": "...", "last_name": "...", "email": "...", "phone": "..." }
Active InINFO_VERIFY_PENDING

4. trigger_otp

DescriptionGenerate a 6-digit OTP and email it to the guest. Code expires in 10 minutes; max 3 verification attempts.
Parameterssession_id (string, required)
Returns{ "otp_sent": true, "email": "j***@example.com", "expires_in": "10 minutes" }

DescriptionRecord that the guest has uploaded their ID document. Updates guest record with file path and marks ID as verified.
Parameterssession_id (string, required), file_path (string, required)

8. generate_incidental_link

15. Troubleshooting

15.1 Ollama Not Running / Model Not Found

Symptoms: Agent responses are slow or use fallback (regex-based) responses. Logs show Connection refused to localhost:11434.

Solution:

  1. Start Ollama: ollama serve
  2. Pull the model: ollama pull llama3.1:8b
  3. Verify: curl http://localhost:11434/api/tags
  4. If running in Docker, ensure OLLAMA_BASE_URL=http://host.docker.internal:11434
Fallback: The system automatically falls back to regex-based intent matching when Ollama is unreachable. Guests can still complete onboarding, but responses will be less conversational.

15.2 MySQL Connection Refused

Symptoms: 503 Service Unavailable on all API calls. Logs show Can't connect to MySQL server.

Solution:

  1. Check container: docker compose ps mysql
  2. Wait for healthcheck: MySQL can take 10-30 seconds on first start.
  3. Verify credentials in .env match docker-compose.yml.
  4. Test connection: docker compose exec mysql mysql -uguestcheckin -pguestcheckin guestcheckin

15.3 MailHog Not Receiving Emails

Symptoms: OTP emails are not appearing in the MailHog Web UI at http://localhost:8025.

Solution:

  1. Check MailHog container: docker compose ps mailhog
  2. Verify SMTP_HOST=mailhog and SMTP_PORT=1025 in the app environment.
  3. Test SMTP: docker compose exec app python -c "import smtplib; s=smtplib.SMTP('mailhog',1025); s.sendmail('test@test.com','guest@example.com','Test'); print('OK')"

15.4 WebSocket Disconnects

Symptoms: Chat widget shows "Disconnected" or stops receiving messages.

Solution:

  1. The widget auto-reconnects with exponential backoff (1s → 30s). If it doesn't, refresh the page.
  2. Check server logs for WebSocket errors: docker compose logs app | grep WebSocket
  3. Verify the session is still active: GET /api/v1/sessions/{id}
  4. Session state is persisted in MySQL — disconnection does not lose progress.

15.5 OTP Not Received

Symptoms: Guest reports not receiving the verification code email.

Solution:

  1. In development, check MailHog at http://localhost:8025.
  2. Verify the guest's email in the reservation is correct.
  3. Trigger a new OTP: the old code may have expired (10-minute window).
  4. In production, check your SMTP provider's sending logs.
  5. OTP delivery retries 3 times internally before reporting failure.

15.6 Rate Limiting

Symptoms: 429 Too Many Requests responses.

Solution: Default rate limit is 60 requests/minute per API key. Adjust RATE_LIMIT in .env if needed.

15.7 Invalid State Transition (422)

Symptoms: 422 Unprocessable Entity when sending a message.

Solution: The LLM detected an intent that doesn't match the current state (e.g., guest said "I agree" while in ID_VERIFY_PENDING). The state machine rejects invalid transitions. The agent should clarify the required action. If the issue persists, check the state via GET /sessions/{id}/state.

16. Glossary

Booking ReferenceA unique code (e.g. BK-2024-001) identifying a reservation in the system.
